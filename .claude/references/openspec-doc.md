# OpenSpec の成果物の書き方（`openspec/changes/**`・`openspec/specs/**`）

この API（NestJS 製の書籍・著者管理 API。Laravel の設計を Laravel の外でどこまで再現・接近できるかを確かめる題材）で OpenSpec の change を書くときの書き方。成果物の構造と見出しは OpenSpec CLI の `openspec instructions <artifact>` が正本で、本書はその上にこのプロジェクトの書き方を足す。要点は `openspec/config.yaml` の `rules:` にも入れてある。仕様の原典はルートの `README.md`。

目指す spec は、**そのエンドポイント群の振る舞いを 1 つの約束として、読むだけで Feature テスト（supertest）と Unit テストを起こせる状態**である。具体的には次を満たす。

- Purpose に、扱う範囲と対象外を 1〜2 文で言い切っている
- 要件が関心ごとに分かれている。おおむね、レスポンスの形 → 取得（公開） → 作成・更新・削除 → 入力検証 → 認証・認可 → 他の機能との関係 → 対象外 の順に並ぶ
- 各要件のシナリオが、境目の値を対で持つ（ちょうど／1 つ超え）
- シナリオの値は具体的で、結果は観察できる形（HTTP ステータス・レスポンスボディのキーと値・DB の件数・その後の API の結果）で書かれている
- 他の capability が扱う範囲は、その名前を挙げて境界を示す（例: 「ログインの失敗は `user-auth` が扱う」）

## spec のシナリオ

**シナリオはそのままテストケースの候補になる。** 代表例を 1 つ書いて終わりにしない。ただし、意味のないシナリオで数を水増ししない。

- 量の目安: 1 要件に 2〜5 シナリオ、1 capability で 10〜25 シナリオ
- 要件は「1 要件 1 振る舞い」に分ける
- 対象外にしたことで、うっかり変えてしまいそうな挙動は、「変わらない」ことをシナリオで確かめる（例: プロフィール更新で `email` を送ってもメールは変わらない）

### 各要件で洗い出す観点

次の観点を要件ごとに当て、該当するものはシナリオにする。

- **境目の対**: 文字数の上限ちょうどと 1 つ超え（`name` 100 文字と 101 文字）、最小値ちょうどと 1 つ下（`password` 8 文字と 7 文字、`price` 1 と 0）、有効期限の直前と直後
- **値の種類**: 未指定・空文字・型違い（文字列の数値、小数）・形式違い（メール形式でない）・`null` を許すか
- **件数の振れ**: 0 件・1 件・複数。0 件のときは空配列 `[]` が返るか
- **認証の状態**: トークンなし・形式不正・署名不正・期限切れ・ユーザーが論理削除済み・一般ユーザー・管理者。401 と 403 のどちらになるか
- **存在の状態**: 存在する・存在しない・論理削除済み（API からは存在しないのと同じに見えるか）。ID が数値でない（400）
- **他のリソースとの関係**: 参照先がない（`authorId`）、一意性の衝突（メール重複。自分自身のメールのままは衝突にしない）、削除の波及（ユーザー削除でリフレッシュトークンも消える）
- **漏らしてはいけない値**: パスワード（ハッシュを含む）がどのレスポンスにも出ない、500 で例外の詳細が出ない
- **時間**: 同じリクエストの中／後続のリクエスト（作成した後に GET できる、削除した後に GET すると 404）

### シナリオの書き方

- WHEN／THEN に**具体的な値**を書く（「`{ "title": "人間失格", "authorId": 3, "price": 550 }` で作成する」「ステータス 422 で `errors.price` がある」）。「正しく処理される」のような値の無い THEN は書かない
- 前提が長いときは **GIVEN** を使ってよい（「GIVEN 管理者でログインしている」）
- THEN は観察できる結果だけを書く。ステータスは数値で、ボディはキーと値で書く
- シナリオ名は短い名詞句にする（「上限ちょうど」「トークンなし」「論理削除済み」）

### 要件の書き方

- 本文は 500 字以内（`openspec validate --strict` の制約）。超える分はシナリオへ移す
- SHALL／MUST／MUST NOT は英語のまま残し、「〜しなければならない（SHALL）」「〜してはならない（MUST NOT）」の形で文に入れる
- エンドポイント（`POST /api/books`）・リクエストとレスポンスの JSON のキー・ステータスコード・エラーメッセージの文言は外から見える約束なので書いてよい
- クラス名・ファイル名・ライブラリ名（`ValidationPipe`、`TypeORM` など）の実装の言葉は spec に書かない（design に書く）
- 新しい capability は `## Purpose` に、扱う範囲と対象外を 1〜2 文で書く
- 既存の要件を変えるときは、要件のブロックを丸ごと写して直す（MODIFIED）。一部だけ書くと archive のときに残りが消える

## proposal

- Why: 何が困っているか・何を確かめたいか（Laravel の構成との対応、レイヤーの責務・依存の向きへの影響）
- What Changes: 箇条書き。変えないもの（範囲外）も書く。API の互換性を壊す変更は **BREAKING** と書く
- Capabilities: 新しい capability／変更する capability。既存の要件が変わらないなら、なぜ変わらないかを一言添える
- Impact: 変わるディレクトリ（`src/http/`・`src/useCases/` など）、API の互換性（既存の spec・クライアントとの差）、依存パッケージ、DB スキーマ（マイグレーションの有無）

## design

- Context に、判断に効く今の作りと README との関係（README のどの節に従うか、README から外れる点）を書く
- Decisions は `### D1. 〜` と番号を振り、見出しに決めたことを書く。本文に「理由」と「代替案（採らなかった案と、その理由）」を書く。tasks や README からは `D1` の番号で参照する
- レイヤーの責務（`domain/` は外部ライブラリに依存しない、UseCase は HTTP を知らない、ドメイン例外 → HTTP の変換はフィルタで一括）から外れる判断は、必ず Decisions に理由を書く
- README から外れる判断をしたら、README 側も直すことを tasks に入れる
- Risks は `[リスク] → 対策` の形で書く

## tasks

- 番号付きのグループに分け、各タスクに確かめ方を書く（`npm run test:feature`・`npm run test:unit` の該当ファイル、`npm run build`・`npm run lint`、`npm run db:*` の実行結果、curl で見ること）
- テストは、それを必要とするグループの中に置く。最後のグループに寄せない
- 新しいディレクトリやレイヤーの規約が変わるときは、そのディレクトリの `README.md` を更新するタスクを同じグループに置く
- 実際に起動して curl で確かめる結合確認は最後のグループに置く

## 書かないこと

- 決まっていないことを確定したように書くこと。未決は design の Open Questions か、未決とわかる書き方で残す
- spec に実装の手順やクラス名（それは design・tasks の役目）
- README と食い違う内容を黙って書くこと。食い違うなら design に理由を書き、README を直す
